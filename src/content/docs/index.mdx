Sprey documentation is the canonical operational memory for the project. It records architecture, deployment choices, verified configuration, recovery implications, and product boundaries from the systems that are actually built and tested.

## Sprey Processing

**Sprey Processing** is Sprey's live non-custodial crypto payment infrastructure and the reference implementation of its **non-custodial crypto acquiring** model.

The product is intentionally broader than a single online-store integration. `pay.sprey.win` is intended to serve businesses accepting crypto **online and in person** through online-store integrations, Point of Sale, QR payment flows, Payment Requests, Payment Buttons and donations, crowdfunding, and API/custom integrations.

Merchant payments go to merchant-controlled wallets or payment destinations. Sprey provides invoice, network-observation, payment-state, and integration infrastructure; it does not initiate, route, receive, hold, or forward merchant funds.

`Sprey WP Stack` is one ready-made WordPress/WooCommerce implementation connected to this broader Processing product. It is not the boundary of `pay.sprey.win`.

## Documentation model

Upstream capabilities and verified Sprey capabilities are deliberately distinguished. A BTCPay feature may belong to the intended Sprey Processing scope before it is configured on `pay.sprey.win`; it becomes a verified Sprey capability only after the real reference deployment has been tested.

The operating rule is simple:

> **Build it. Verify it. Document it.**
